# Conformance Carve-Outs

Every `.ball.json` in this directory **must** be regenerable from a Dart source in
`src/<name>.dart` via `dart run bin/generate_conformance.dart` (from `dart/encoder`),
**except** the fixtures listed below. These are the only fixtures allowed to exist
without a matching `src/<name>.dart`. The gate
`dart run bin/check_conformance_sources.dart` (CI: the `ball-freshness` job) fails if
any *other* `.ball.json` lacks a source, or if a name listed here no longer exists.

The carve-out name is the leading backticked token on each `-` bullet below — keep
that format; the gate parses it.

## Host-policy behavioral fixtures

These programs validate engine **error/limit behavior**, not stdout, so they have no
`.expected_output.txt` and cannot be run by `dart run` (an infinite loop / unbounded
allocation / oversized program / sandboxed I/O). Each is asserted behaviorally by the
engine test harnesses instead — `dart/engine/test/conformance_test.dart` and
`cpp/test/test_selfhost_conformance.cpp` (the `HostKnob` table).

- `196_timeout` — `while(true){}`; engine must raise "Execution timeout exceeded" under `timeoutMs`.
- `197_memory_limit` — unbounded `list_filled`; must raise "Memory limit exceeded" under `maxMemoryBytes`.
- `201_input_validation` — oversized program; must raise "Too many modules" / "Expression too deep" / "Program too large".
- `202_sandbox_mode` — `file_read` under `sandbox: true`; must raise "Sandbox violation".

## Tool-generated fixtures

- `256_editions_resolver` — generated by `dart/encoder/tool/gen_editions_conformance.dart`
  (runs the real Editions feature resolver), not by the Dart-source encoder pipeline.

## Feature-gap carve-outs

- `188_std_time_now` — exercises the `std_time` base module (`format_timestamp` /
  `parse_timestamp` over a fixed epoch). The syntactic encoder has no routing for
  `DateTime` / `dart:convert`-style time APIs to `std_time`, and the engine's
  `now()`-derived components are host-controlled (non-deterministic), so it cannot be
  generated from portable Dart source. Hand-authored; revisit if `std_time` encoder
  routing + a mockable clock are added.
- `389_typed_to_string` — exercises `std.int_to_string` / `std.double_to_string`.
  These are type-specific variants of `to_string`; the syntactic encoders have no
  static type resolution, so `.toString()` always routes to the generic
  `to_string` and can never disambiguate by receiver type. Generated by
  `dart/encoder/tool/gen_std_gap_fixtures.dart` (issue #64 std-coverage gap).
- `390_goto_label` — exercises the `label` / `goto` base functions (a backward goto
  loop printing `0,1,2`). No source language surfaced by an encoder has a
  `goto`/label statement, so it cannot be generated from portable source. Hand-authored
  (issue #184); it is the regression guard for the C++ self-host label loop — the
  reified thrown `_FlowSignal` fix in `engine_control_flow.dart._gotoSignalLabel`.
- `459_set_add_remove_bool` — exercises `std_collections.set_add` / `set_remove` with
  both results in a VALUE position (issue #545). No portable Dart source encodes to
  these: the Dart encoder deliberately DECLINES to route a `Set` receiver's
  `.add()`/`.remove()` to them (the receiver-type gate in `dart/encoder/lib/encoder.dart`,
  issue #488), so `s.add(x)` re-emits as a generic method call, never as `set_add`.
  Generated by `dart/encoder/tool/gen_std_gap_fixtures.dart` alongside `389`/`390`.
  It is the cross-target guard for the one bool contract — before #545 the Dart
  engine returned the NEW SET from both (and never mutated the receiver), the Dart
  and C++ compilers returned the set, and the TS engine returned an unconditional
  `true` from `set_add`. **Each case uses a FRESH set** rather than chaining calls
  against one `let`-bound set, so this fixture pins the RETURN-VALUE contract only.
  The chained form — one set, mutated and then read back — is
  `460_set_mutation_in_place` below, added with the fix for issue #557; the two
  fixtures cover different halves of the same contract, so keep both.
  For the same reason it is inexpressible in Dart, it also cannot survive the
  **`dart-roundtrip`** leg of `dart/compiler/test/conformance_roundtrip_test.dart`
  (Ball → Dart → *encoder* → Ball' → Dart): the compiled `a.add(3)` needs the
  receiver's TYPE to re-encode as `set_add`, and the syntax-only encoder has none,
  so it routes to `list_push` and compiles back to the cascade `a..add(3)` — the set,
  not the bool. That one leg is the sole entry in that harness's
  `_knownUnroundtrippable` ratchet (which fails if the entry ever starts passing);
  the fixture's `engine`, `dart-compiled` and `ts-compiled` legs all pass. Issue #488
  owns the receiver-type seam that will delete the entry.
- `460_set_mutation_in_place` — the IN-PLACE half of `std_collections.set_add` /
  `set_remove` (issue #557): one `let`-bound set is created once, added to, removed
  from, and then READ BACK — printed whole, measured with `set_length`, and probed
  with `set_contains` for both the added and the removed element. Hand-authored for
  the same reason `459` is (the receiver-type gate, issue #488, means no portable
  Dart source encodes to a `set_add` call), by the same tool,
  `dart/encoder/tool/gen_std_gap_fixtures.dart`.
  It is the regression guard for #557: the C#, Rust and C++ self-hosted engines all
  printed `{1, 2}` for the whole set while every bool AND `set_length` still looked
  right, because their compiled `_ballSetItems` handed back a COPY of the backing
  list (its `v is Map` guard is false for a tagged set on those targets since
  #528/#553, so the native-`Set` `.toList()` branch ran instead). Only reading the
  SAME set back after a mutation can see that — which is exactly why `459`'s
  fresh-set-per-case form could not, and why this fixture must never be rewritten
  to use a fresh set.
  Like `459`, it cannot survive the **`dart-roundtrip`** leg of
  `dart/compiler/test/conformance_roundtrip_test.dart` (its first line is a
  `set_add` result in a value position, and the compiled `a.add(3)` re-encodes to
  `list_push` → the cascade `a..add(3)` → the SET). It is the second and last entry
  in that harness's `_knownUnroundtrippable` ratchet; issue #488 owns the seam that
  will delete both. The fixture's `engine`, `dart-compiled` and `ts-compiled` legs
  all pass.
- `399_bytes_literal` — exercises a `Literal.bytes_value` node (the `literal.bytes_value`
  node-shape carve-out, #64 Phase 2b). No Dart source construct maps to a bytes literal
  (`Uint8List.fromList([...])` encodes as a constructor call), so it cannot be generated
  from portable source. Hand-authored; it is the regression guard for issue #244 (the
  TS and C++ compilers, plus the self-hosted TS engine, all discarded a bytes literal's
  real content before that fix).
